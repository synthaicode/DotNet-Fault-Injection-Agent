# DotNet Fault Injection Agent

[計画から指定する CoreCLR 呼び出し注入](../../poc/scenarios/PlanDrivenInjection/README.md)を追加しました。
対象と呼び出し箇所をソース・PDB・DLLで照合し、条件・障害・発火上限を version 3 の
計画で指定します。Linux x64 / .NET 8 の検証範囲と実行手順はリンク先に記載しています。

.NET Frameworkで動くWindowsサービスを対象に、指定した処理で障害を起こし、例外処理や復旧動作を評価するためのツールです。設計と検証用PoCを公開しています。

## 目的と制約

- 対象サービスの業務ソースを変更・再ビルドせず、配布済みのEXE・DLLを維持する。対象プロセス内でのIL書換えを候補とする。
- 介入を指定したプロセス内に絞る。共有ロックや外部システムを通じた間接影響は試験ごとに評価する。
- 利用者は業務処理、発火条件、再現したい障害を指定する。C++、IL、メタデータトークンはツール内部で扱う。

## 指定から実行まで

1. Roslynでプロジェクトと参照を解決し、呼び出し元、API、ソース位置、周辺の例外処理を抽出する。AIは利用者の意図と候補を結び付け、選定理由と静的に確定できない値を示す。
2. 利用者が箇所、条件、障害を確定する。たとえば注文確定処理で、検証DBの特定のストアドプロシージャを呼ぶ場合だけ、最初の一回を送信前に失敗させる。共通ヘルパーで複数の業務経路が合流し、条件で識別できない場合は適用を止める。
3. 構造化ルールを対応APIと障害種別の一覧に照合する。PoCではPEとPortable PDBの識別情報、PDBのソースチェックサム、シーケンスポイントとILを確認し、呼び出し命令を一意に特定できる場合に限り注入計画を作る。計画はモジュールのハッシュとMVID、メソッドトークン、ILオフセット、期待する呼び出し先に結び付ける。
4. 外部AgentはEXEの絶対パス、PID、プロセス作成時刻で対象を照合し、有効化と無効化を管理する。プロセス内モジュールはロード済みモジュールと命令を照合し、コマンド種別、接続先、DB、プロシージャ名が一致したときだけ発火する。無効時や不一致時は元のAPIへ通す。
5. 計画受理、IL書換え、JIT結果、有効化、実際の発火を別々に記録する。例外処理・復旧の結果はアプリ側で観測する。無効化で後続の呼び出しを通過させる操作と、ILの復元は区別する。

アプリが特定番号のSqlExceptionを捕捉する場合、その分岐を試すには対応する例外が必要です。最初のPoCで候補とするTimeoutExceptionは、介入経路の確認に使います。対応する生成方式がない障害は理由付きで適用前に拒否します。送信前に失敗する試験と、DB処理後に応答が失われる試験は分けます。

## 介入方式の候補

- **CLR Instrumentation Engine**。プロファイラーのホストとIL命令グラフを利用する。ネイティブ拡張、介入対象の選択、中継処理、ルール照合、Agentとの連携は実装が必要。PoCで先に試す。 [設計資料](https://github.com/microsoft/CLRInstrumentationEngine/blob/main/DESIGN-NOTES.md)
- **CLRプロファイラーの自作**。ロードと書換えを直接制御できる。COMの入口、CLRコールバック、分岐や例外処理領域を含むIL操作、アーキテクチャ別の配布を自前で扱う。既存基盤でロードや必要な書換えが成立しない場合に再評価する。 [CLRの起動設定](https://learn.microsoft.com/en-us/dotnet/framework/unmanaged-api/profiling/setting-up-a-profiling-environment)

## 最小PoCの合格条件

専用の非本番環境で、一度ビルドして固定した.NET Frameworkのテストプログラムと検証DBを使う。初回JITで、アプリ側の同期System.Data.SqlClient.SqlCommand.ExecuteNonQuery()の呼び出し一箇所に介入する。起動後に介入点を追加する必要が出た段階でReJITを検討する。

- ソースから候補を選べる。異なる配布物やPDB、曖昧な命令対応は適用前に拒否できる。
- 選んだ箇所で条件が一致したときだけ、送信前にTimeoutExceptionが発生する。同時に複数回一致しても、有効化後の発火は一回に収まる。
- 同じプロシージャを呼ぶ別箇所、選んだ箇所の別コマンド、別プロセス、無効時、発火後の再呼び出しは通常どおり動く。
- 発火した呼び出しで対象コマンドが送信されなかったことをDB側で確認できる。アプリの例外処理を観測でき、配布EXE・DLLのハッシュは試験前後で一致する。
- 未対応のSqlExceptionや非同期APIの指定は実行前に拒否できる。将来のTask対応では、同期で投げる失敗と失敗したTaskを返す挙動を区別する。
- テストプログラムで成立した後、専用Windowsサービスの起動でもプロファイラーのロードとプロセスの限定が成立することを確認する。

## 未確認事項

プロファイラーのロード、IL書換え、発火およびWindowsサービスでの動作は未検証です。実装前に検証環境のWindowsと.NET Frameworkのバージョン、プロセスのビット数、SqlClient、既存APM、サービスの起動構成、配布物に対応するソースとPDBを確認します。NGenとインライン化が対象メソッドの介入に与える影響も検証します。ルールのファイル形式とAgentの通信方式は未決定です。
