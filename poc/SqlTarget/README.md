# 同期SQL呼び出し一箇所の介入検証

.NET Framework 4.8向けのx64テストプログラムです。ローカルの SQL Server LocalDB の MSSQLLocalDB を使い、同一接続内に一時テーブルと二つの一時ストアドプロシージャを作成します。接続終了で一時オブジェクトは破棄されます。

リポジトリのルートで `dotnet build poc/SqlTarget -c Release` を実行し、生成された SqlTarget.exe を使います。[拡張のビルドと起動条件](../ProfilerRewrite/README.md)に従い、プロファイラー無効、選択箇所用の[JSON計画](../SourceMap/README.md)と拡張あり、プロファイラー無効の順に、同じEXEを起動します。

| 起動 | 選択した箇所で対象プロシージャ | 別の箇所で対象プロシージャ | 選択した箇所で別プロシージャ | 一致する二回目の呼び出し | DBの記録行数 |
|---|---|---|---|---|---:|
| 無効 | 成功 | 成功 | 成功 | 成功 | 4 |
| 拡張あり | TimeoutException | 成功 | 成功 | 成功 | 3 |
| 無効 | 成功 | 成功 | 成功 | 成功 | 4 |

全起動の終了コードは0で、試験前後のEXEのSHA-256は一致しました。エンジンのログにも選択したメソッドの書換え成功が記録されました。

選択箇所のILでは、ソース上の SqlCommand からの呼び出しが DbCommand.ExecuteNonQuery の仮想呼び出しとして記録されます。拡張はその呼び出し命令を、テストEXEにあらかじめ組み込んだ専用ヘルパーへの呼び出しに置き換えます。ヘルパーは接続先、DB、コマンド種別、プロシージャ名がJSON計画の条件に一致する場合に、SQL APIに進まず例外を投げます。既定の計画では一致した最初の一回だけ発火枠を取得します。上限到達後と不一致の場合は元のAPIを呼びます。別箇所と不一致の呼び出しを先に実行し、発火枠を消費しないことも確認しました。条件不一致の試験ではプロシージャ名だけを変えています。DB側はプロシージャが行ったINSERTの件数を確認しています。SQL通信のトレースはこの検証では採取していません。

SqlTarget.exe に --concurrent を渡すと、別々の接続を使う二つのタスクがバリアで揃ってから同じ対象箇所を呼びます。拡張ありでは一方だけが TimeoutException になり、もう一方は正常に終了しました。拡張なしでは両方が正常に終了しました。発火枠はプロセス起動ごとに初期化されます。

対象は固定のテストメソッドです。既存アプリへのヘルパー提供、Roslynと配布物の対応確認、SqlExceptionによるSQLタイムアウト再現は未実装です。

## JSON計画の条件を変更した試験

同じEXEと同じ呼び出し箇所に対し、各試験でJSONの値だけを一つ変更しました。

| 変更 | 発火回数 | DBの記録行数 |
|---|---:|---:|
| 既定値 | 1 | 3 |
| 接続先を不一致に変更 | 0 | 4 |
| DBを不一致に変更 | 0 | 4 |
| プロシージャ名をもう一方へ変更 | 1 | 3 |
| 上限を2へ変更 | 2 | 2 |
| 上限を0へ変更 | 0 | 4 |

上限が負数の計画は拒否されました。上限1での同時実行では一方だけ発火しました。試験前後でEXEのSHA-256は一致しました。接続先とDBの条件は照合にのみ使います。JSONを変えてもアプリの接続先は変わりません。検証済みの条件はプロファイラーから検証用ヘルパーへプロセス内の環境変数で渡します。

## 検証用ランチャー

PowerShell 7で、対象EXE、JSON計画、CLR Instrumentation EngineのDLL、拡張のXML設定を指定します。

```powershell
./poc/SqlTarget/Invoke-SqlTarget.ps1 -Target $exe -Plan $plan -Engine $engine -ExtensionConfig $config
```

同時実行試験には -Concurrent を追加します。ランチャーは検証用の子プロセスにだけ起動設定を渡し、終了コード、計画受理と拒否の記録、IL書換え、発火回数、元の出力を別々に返します。受理後にロード済みモジュールの照合で拒否される場合があるため、受理と拒否はそれぞれ記録の有無を表します。終了コード0でも、発火したかどうかは発火回数で確認します。ローカルの未署名拡張を使うため、署名検証の無効化は検証用の子プロセスに限定します。

既定の計画で一回発火、上限0で書換えのみ、負の上限で計画拒否と書換え・発火なしを確認しました。

## 起動中に有効・無効を切り替える試験

Program.Selected を選んで現在のEXE用のJSON計画を生成し、maxFirings を2に設定します。同じ子プロセスへ標準入力でコマンドを順に送り、標準出力で応答を受け取ります。

```powershell
./poc/SqlTarget/Invoke-SqlTarget.ps1 -Target $exe -Plan $plan -Engine $engine -ExtensionConfig $config -ControlSequence call,enable,call,disable,call,enable,call,call
```

| 呼び出し時の状態 | 結果 |
|---|---|
| 起動直後の無効 | SQL実行成功 |
| 有効化後 | TimeoutException |
| 発火枠が1回残った状態で無効化 | SQL実行成功 |
| 再有効化後 | TimeoutException |
| 発火枠を使い切った後 | SQL実行成功 |

有効化と無効化はプロセス内ヘルパーの発火判定に反映されます。無効化は発火枠を消費せず、再有効化は発火枠をリセットしません。試験は一つのPIDで完了し、終了コードは0、発火記録は2回、試験前後のEXEのSHA-256は一致しました。

制御コマンドとSQL呼び出しは専用の検証モードで直列に処理します。独立したAgentからの接続、実行中の呼び出しと無効化が競合した場合の挙動、既存Windowsサービスの制御は未検証です。

## 二箇所を同じ計画で実行する試験

Selected の上限を2、Other の上限を1に設定し、同じJSON計画で起動しました。同じプロシージャに対して Selected で2回、Other で1回発火し、別プロシージャの呼び出しは成功しました。DBへの記録は1件でした。書換えと発火のログに methodToken を含め、ランチャーの FiringsByMethod で箇所別の件数を集計します。

重複した対象を含む計画は全体が拒否され、書換えと発火は0回でした。従来形式の単一ルールは引き続き動作し、試験前後で同じEXEのSHA-256が一致しました。

## 三箇所の試験

SourceMapの候補から Selected、Other、Third を選んで一つのJSONを生成し、ランチャーに -ThreeSites を渡します。Selected は #ConfirmOrder を2回、Other は #ConfirmOrder を1回、Third は #OtherOrder を1回まで失敗させる条件に設定しました。同じPIDで箇所別に2回、1回、1回発火し、条件不一致と上限到達後の呼び出しは成功しました。DBへの記録は2件で、試験前後のEXEのSHA-256は一致しました。
